# CubeVision

A mobile-first Rubik's Cube solver. Scan all six faces with your camera, and CubeVision
detects the colors, validates the cube is actually solvable, computes an optimal
solution with Herbert Kociemba's two-phase algorithm, and walks you through it move
by move on an animated 3D cube — entirely offline, no backend.

Built with React Native + Expo + TypeScript.

## How it works

1. **Scan** — guided camera capture of all 6 faces (or 5, see below), with a live
   3×3 overlay and automatic capture once the cube holds still.
2. **Detect** — sticker colors are classified in CIE L\*a\*b\* space (not raw RGB),
   which is far more robust to lighting changes than naive color matching, and the
   classifier adapts to your camera/lighting as you confirm each face.
3. **Review** — every detected face is shown before it's committed; tap any sticker
   to correct it.
4. **Validate** — before solving, the scanned state is checked against the real
   mathematical constraints of a Rubik's Cube (piece identity, permutation parity,
   corner/edge orientation) so an unsolvable scan is caught immediately, with a
   pointer to exactly which face to rescan.
5. **Solve** — [`cubejs`](https://github.com/ldez/cubejs), a JS implementation of
   Kociemba's two-phase algorithm, computes a solution in ≤22 moves.
6. **Play back** — an animated, gesture-controlled 3D cube steps through the
   solution forward/backward, with optional spoken move-by-move voice guidance.

## The "smart 5-face scan"

The spec's stretch goal — inferring the sixth face instead of always scanning it —
is implemented as a real constraint solver, not a heuristic: every corner and edge
piece on a Rubik's Cube has a fixed, unique combination of colors, so once 5 faces
are scanned, most of the last face's stickers are already implied by the physical
pieces you've already seen elsewhere. `src/cube/inferSixthFace.ts` performs a
bounded backtracking search over the remaining piece assignments and only accepts
a candidate that produces a fully solvable cube.

This was validated against 1,000 random cube states generated by `cubejs` itself:
it resolves the sixth face outright in **~90% of cases with zero incorrect
answers** across every trial — the remaining ~10% fall back to asking the user to
scan the last face normally, exactly as the spec allows ("asking for the last face
only if needed"). See the algorithm's own doc comment for the full reasoning.

```
  navigation/      React Navigation stack
  theme/           Shared design tokens
```

## Why the cube geometry is trustworthy

Rather than hand-deriving which sticker positions belong to which physical corner/edge
piece (an easy place to introduce an off-by-one or mirrored error), `src/cube/geometry.ts`
and `src/cube/cubieGeometry.ts` were transcribed directly from `cubejs`'s own facelet
definitions and cross-checked against it — see the derivation notes in those files. The
whole pipeline (facelet round-tripping, validation, sixth-face inference, and actually
solving and verifying the solution un-scrambles the cube) was run end-to-end against
`cubejs` outside of React Native as part of building this scaffold; see "Known
limitations" for what still needs on-device verification.

## Setup

```bash
cd CubeVision
npm install
npx expo start
```

Requires a native dev client (or `expo run:android` / `expo run:ios`) rather than plain
Expo Go, because `expo-gl` (used for camera pixel sampling) and `expo-camera` need
native modules Expo Go doesn't bundle by default.

## Known limitations

This app was built and verified in a headless environment with no physical device,
camera, or GPU to test against. Everything that's pure logic — the facelet model,
validation math, sixth-face inference, and the solver integration — was compiled and
run against real `cubejs`-generated cube states and confirmed correct (see above).
The parts that genuinely need on-device verification before shipping:

- **Pixel color sampling** (`src/camera/pixelSampler.ts`): uploads each captured
  photo into an offscreen `expo-gl` context and reads sticker colors back with
  `readPixels`. This is a real, documented technique, but it's the one piece of the
  app that can't be exercised without an actual camera and GPU — verify sample
  coordinates and color accuracy on-device, and tune `ColorProfile`'s starting
  reference colors for your target lighting conditions if needed.
- **Stability-based auto-capture** (`src/camera/useStableFrame.ts`): polls
  low-res stills on an interval to detect when the cube has stopped moving. The
  thresholds (`STABLE_DIFF_THRESHOLD`, `STABLE_FRAMES_REQUIRED`, poll interval) are
  reasonable starting points, not device-tuned values.
- **Guided-scan orientation hints** (`src/cube/scanRoles.ts`): the "put color X at
  the top edge" instructions assume the standard Western/BOY color scheme. A cube
  with a mirrored ("Japanese") scheme will scan as unsolvable and needs a settings
  toggle (not yet built) to correct for.
- **3D cube rendering/animation** (`src/components/Cube3D.tsx`): the rotation math
  (which layer moves, which axis, which direction is clockwise) was worked through
  carefully and cross-checked against the same verified geometry table everything
  else uses, but rendering behavior itself needs visual confirmation on-device.
- **cubejs runs on the JS thread**: `Cube.initSolver()` takes a few seconds and
  there's no worker-thread option in Hermes/React Native, so it's kicked off early
  (on the Home screen) rather than when the user reaches the Solve screen — but a
  very fast tap-through could still hit a brief wait.
